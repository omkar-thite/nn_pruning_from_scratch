# System Design: Dynamic Structural Pruning Engine

## 1. Importance Criterion Derivation

The pruning criterion relies on the first-order Taylor series expansion of the loss function $L(W)$ with respect to the weights $W$. 

$$L(W - \Delta W) \approx L(W) - \nabla_W L(W) \cdot \Delta W$$

Removing a specific weight $w_{ij}$ is equivalent to setting $\Delta w_{ij} = w_{ij}$. Therefore, the approximate change in the loss function due to the removal of $w_{ij}$ is:

$$\Delta L \approx - \frac{\partial L}{\partial w_{ij}} w_{ij}$$

To measure the magnitude of this impact regardless of its direction, the absolute value is taken:

$$I_{ij} = \left| \frac{\partial L}{\partial w_{ij}} w_{ij} \right|$$

Because the implementation performs structured pruning (removing entire neurons rather than individual connections), the importance of a neuron $j$ is the sum of the importances of all its incoming weights. This corresponds to summing over the input dimension (`axis=0`) of the weight matrix:

$$I_j = \sum_i \left| \frac{\partial L}{\partial w_{ij}} w_{ij} \right|$$

This perfectly matches the engine's implementation `np.sum(np.abs(W_arr * W_grad), axis=0)`. It approximates the loss change efficiently using only first-order gradients, avoiding the intractable computation of the full Hessian matrix.

## 2. Gradient of a Masked Weight

During standard training iterations, the engine physically resizes the weight matrices (`sync_to_network()`), isolating only the active neurons. Consequently, the gradient of a structurally pruned weight is never computed; it is implicitly zero, and the memory corresponding to its activation and gradient is not allocated.

During the periodic pruning probe step, the full dense architecture is temporarily reinstated (`masks = np.ones_like(masks)`). A forward and backward pass is executed to compute the exact gradient of all weights (including previously pruned ones) with respect to the current batch. 

This is the optimal choice for structural pruning. Applying a binary mask to a dense matrix during every forward/backward pass wastes FLOPs on zero-multiplications. By physically extracting the active sub-matrices, the engine accurately reflects the hardware-level computational benefits of pruning. Reinstating the full matrix only during periodic evaluation allows the network to dynamically revive previously pruned connections based on current batch gradients, preventing premature structural collapse.

## 3. Autodiff Engine Bottleneck and Optimization

- The primary bottleneck is the Python-level overhead incurred during dynamic graph construction (`build_graph()`) and reverse topological traversal (`backward()`). Every mathematical operation allocates a new `Tensor` object, initializes a gradient array, and defines a unique lambda closure (`_backward`). Python's object allocation, garbage collection, and recursive function call overhead dominate execution time, significantly overshadowing the underlying NumPy C-level array computations.

- **`build_graph()` is rebuilt from scratch on every `backward()` call.** It does a full recursive DFS with a `visited` set, in pure Python, over the entire `_parents` chain — and this happens once per training step, even though the *structure* of the graph (which operations chain into which) is identical across steps for a fixed architecture; only the data changes. This is pure topology re-derivation work that produces the same ordering every time the architecture doesn't change between calls.

**Optimization Strategy:**

- **Compiled Backend:** Move the tensor abstraction and topological sorting to a compiled backend (e.g., C++ via pybind11) to bypass the Global Interpreter Lock (GIL) and execute graph traversals natively.

- **Vectorize away the graph-walk for fixed architectures.** Since the MLP's connectivity doesn't change within an epoch (only the weight values do, except at sparse pruning events), the topological order from `build_graph()` could be cached and only invalidated when the network is actually restructured (i.e., right after `sync_to_network()` in the pruner), rather than recomputed every `backward()` call.

## 4. Serving a Self-Pruned Model in Multi-Tenant Inference

Because the dynamic pruning method yields a structurally pruned model (physically smaller, dense matrices rather than sparse matrices padded with zeros), serving it relies on standard dense matrix optimizations.

1.  **Stateless Export:** The `master` dense state, optimizer moments, and masks are discarded post-training. Only the final, dimensionally reduced sub-networks (e.g., a 64x50 matrix instead of 64x100) generated by `sync_to_network()` are exported to standard representation formats like ONNX.
2.  **Hardware Utilization:** The exported model utilizes standard highly-optimized BLAS kernels (e.g., cuBLAS). Modern accelerators achieve maximum utilization on smaller dense matrices, successfully bypassing the memory access irregularities and poor cache locality associated with sparse matrix representations (< 95% sparsity).
3.  **Multi-Tenant Batching:** In a real-time service, routing logic must dynamically group incoming inference requests by tenant topology. Because the structurally pruned models occupy a reduced memory footprint, hundreds of unique tenant models can reside in GPU VRAM simultaneously.
4.  **Dynamic Batch Resizing:** Batches of identical topology requests are dispatched to continuous memory blocks, maximizing throughput via standard dense matrix multiplications.
